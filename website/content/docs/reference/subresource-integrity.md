# Subresource Integrity for CDN Loads

> vellar-sdk is published to npm, and npm packages are automatically mirrored by
> CDNs like [unpkg](https://unpkg.com) and [jsDelivr](https://www.jsdelivr.com).
> If you load the SDK from one of those CDNs instead of installing it from npm,
> this page shows how to pin an `integrity` hash so the browser refuses a
> response that does not match the exact bytes you reviewed.

By the end of this page you will know why a CDN load needs a hash a bundled
install does not, how to get the right hash for the version you are loading,
and how to verify it yourself before trusting it.

## Why this matters

Installing from npm (`npm install vellar-sdk`) and bundling the SDK into your
own build already gives you byte-for-byte reproducibility: the code that ships
is the code in your lockfile, and your own build pipeline is the only thing
between the npm registry and your users.

Loading from a CDN removes that step. A `<script>` tag pointed at
`unpkg.com` or `cdn.jsdelivr.net` trusts the CDN, at request time, to serve
exactly what npm published for that version, every time, for as long as your
page exists. CDNs are generally reliable, but "generally reliable" is not the
same guarantee a lockfile gives you, and a single compromised or misconfigured
edge node is enough to serve a tampered file to a subset of visitors.

[Subresource Integrity (SRI)](https://developer.mozilla.org/en-US/docs/Web/Security/Subresource_Integrity)
closes that gap at the browser level. You tell the browser the exact hash of
the file you reviewed, and the browser refuses to execute anything that
doesn't match, regardless of what the network handed it.

## Using it

```html
<script
  src="https://cdn.jsdelivr.net/npm/vellar-sdk@0.6.2/dist/index.js"
  integrity="sha384-REPLACE_WITH_THE_HASH_FOR_THIS_EXACT_VERSION"
  crossorigin="anonymous"
></script>
```

- Pin an **exact version** in the URL (`@0.6.2`, never `@latest` or an
  unpinned `@0`). SRI hashes a specific file's bytes, and those bytes change
  on every release, so an unpinned URL and a pinned hash will eventually
  disagree and the browser will (correctly) block the load.
- `crossorigin="anonymous"` is required alongside `integrity` for a
  cross-origin `<script>` tag; without it, the browser cannot read the
  response to verify it.

## Getting the hash

### Option A: from the published release (recommended)

Starting with the release that ships this page, every tagged release's GitHub
Release notes include a `dist/sri-hashes.json` listing the SRI hash for every
file in that version's `dist/`, generated by
[`scripts/generate-sri-hashes.mjs`](https://github.com/Vellar-Wallet/vellar-sdk/blob/dev/scripts/generate-sri-hashes.mjs)
as part of the release workflow, before `npm publish` runs. Look up the file
you're loading (for example `dist/index.js`) in that version's hash list and
use the value as-is in your `integrity` attribute.

### Option B: compute it yourself

You do not have to trust the published list. Compute the hash directly from
the file you intend to load, and compare:

```sh
# Download the exact file your <script> tag points at:
curl -sL https://cdn.jsdelivr.net/npm/vellar-sdk@0.6.2/dist/index.js -o index.js

# Hash it (sha384 is what SRI/browsers expect; sha256 and sha512 also work):
openssl dgst -sha384 -binary index.js | openssl base64 -A
```

Prefix the result with `sha384-` to get the full `integrity` value. If it
matches the one in the release notes, you have independently verified that the
CDN is serving what npm published, not something injected in transit.

### Option C: generate it from a local build

If you built the SDK yourself (`npm run build`), you can generate the same
hash the release workflow would, for every file in `dist/`, with:

```sh
node scripts/generate-sri-hashes.mjs
```

Add `--write` to also save the output to `dist/sri-hashes.json`.

## Multiple entry points, multiple hashes

vellar-sdk publishes more than one entry point (`dist/index.js`,
`dist/balances.js`, `dist/rpc.js`, and others — see `package.json`'s
`exports`). Each file has its own SRI hash. If you load more than one
entry point from a CDN, pin the `integrity` attribute for each `<script>`
tag separately; a hash computed for `dist/index.js` will not validate
`dist/balances.js`, by design.

## When it fails

| Symptom | Cause | Fix |
| --- | --- | --- |
| The script silently fails to execute, no console error in older browsers | `integrity` mismatch, or missing `crossorigin` | Confirm you hashed the exact file and version in the `src` URL, and that `crossorigin="anonymous"` is present |
| `Failed to find a valid digest ... in the 'integrity' attribute` (console) | The CDN served different bytes than the hash expects, most often because the URL isn't pinned to an exact version | Pin an exact version, not `@latest` |
| The hash I computed doesn't match the release notes | You hashed a different file, a different version, or an intermediate proxy/cache altered the response | Re-download directly from the CDN origin and recompute; if it still disagrees, do not load the file and open an issue |
